Line Rider procedural track compiler

handoff compiler

The current v0 compiler is a deterministic prefix search. It turns a musical spec into a rideable Line Rider track by extending one contact gap at a time, scoring every partial output, and returning the best track seen before the simulated-physics budget runs out.

The compiler in one page

Handoff compiles from authored intent to physics-validated geometry. The policy is fixed and deterministic for a given spec and seed; the budget only decides how much of that deterministic search sequence is explored.

Mental model

Spec -> gaps -> catches -> track

A spec names a duration, contacts, and axis target curves. Contacts are the beats the rider must hit; curves describe what the ride should feel like between those beats.

1
Read the spec
Validate the spec, convert contact times to frames, split the timeline into gaps, and samples each gap's axis targets (from the curves) with the seeded RNG.
2
Choose starts
Resolve the default or manual start. If preroll gives permission and no manual start is set, rank up to ten deterministic initial velocity options with a small opening feasibility probe.
3
Search prefixes
Pop a prefix from the frontier, evaluate it, then extend the next contact gap with the top-ranked candidate catches. Skip-free prefixes are always explored before fallback prefixes.
4
Validate physics
Candidate catches are not guessed into the output. Each survivor is placed into the lr-core engine and measured through detector reports.
5
Return best seen
The strict register prefers contract-passing tracks, then better achieved style. If the budget ends early, the best honest partial output is still available.
speedAuthored pace mapped to raw px/frame.
airHow airborne or grounded the ride should be.
grainHow large and coarse the generated catch geometry feels.

Data model

What a search node contains

The compiler never needs to rebuild a full track to branch. A node is the engine state after a committed prefix plus enough bookkeeping to extend the next gap deterministically.

SearchNode

  • gapIndex: next gap to expand.
  • prefixFits: committed catch fits or null for non-contact/skipped gaps.
  • prefixEngine: lr-core state after the prefix.
  • prefixNextLineId: stable line ids for new geometry.
  • cumulativeCost: local candidate cost sum, used for diagnostics and ordering.
  • _candidatesCache: memoized candidates for this gap.

HandoffNode

  • Wraps the search node with the selected start state and start rank.
  • Tracks whether start alternatives have been expanded.
  • Tracks candidate ranks per gap for diagnostics.
  • Counts skipped contacts so fallback branches can be deprioritized.
  • Can defer expansion after a skip so honest partial outputs are evaluated first.
Frontier

Two stacks, one deterministic order

The frontier is split into a pass stack and a fallback stack. The pass stack is drained first, so a branch that has landed every contact so far always gets priority over one that has skipped a contact.

Arc placement

How one catch becomes a landing

A candidate is not an absolute line picked from the canvas. The compiler samples a local arc shape, chooses one local impact point on that arc, translates the whole arc so that point meets the predicted sled at the target contact frame, then asks lr-core whether the result really lands and survives.

1
Read target state
At gap.endFrame, the prefix engine predicts the rider without the new catch. readTargetState records the rider velocity and chooses the lowest sled point among PEG, TAIL, NOSE, and STRING as the intended contact anchor.
2
Sample local arc
sampleArcParams samples length, segment count, start angle, end angle, and curve bias. Grain targets steer segment count; brake mode uses an uphill-entry angle band; air-support mode uses longer, shallow catches. The arc is still local geometry with anchor = (0, 0).
3
Pick impact point
In default impact-anchor mode, impactT is an along-arc coordinate, not a time. Current default sampling is clamp(0.6 + jitter, 0.15, 0.85). The compiler evaluates the local point and tangent at that impactT, adds small tangent/normal jitter, and translates the entire arc so the chosen point sits under the predicted sled.
4
Preclear
arcToLines turns the placed arc into solid track lines. Before running a full candidate simulation, the compiler scans the prefix rider from gap.startFrame through gap.endFrame - 2. If any sled point comes within the collision-risk distance of the new lines, the candidate is rejected as a likely pre-beat collision.
5
Direct validation
The candidate lines are added to lr-core and detector events are read. A fit survives only if the rider lives through the required margin, an owned landing event occurs at gap.endFrame +/- 1, and no off-beat landing occurs before the measurement boundary. Only then are speed, air, and grain measured for ranking.
local = arcLocalPointAt(baseArc, impactT) normal = (-local.tangentY, local.tangentX) anchor = targetSled - local + tangent * alongJitter + normal * normalJitter

What impactT actually controls

Moving impactT changes the tangent, curvature, and amount of arc before and after the intended contact point. It also changes which parts of the arc can collide with the rider before the beat. The downstream gates are binary: a small placement shift can delete a candidate from the pool rather than merely making it a lower-quality candidate.

Why the global constant is fragile

A low value such as 0.2 can avoid many preclear rejects, but in the current arc family it usually presents the wrong local catch shape at the beat and fails the owned-landing gate. A back-half value near 0.6 preclears more often, but the survivors land dense high-speed gaps much more reliably. A smarter compiler could make 0.05 work by generating a different local shape and clearance envelope; this compiler only translates the same sampled arc family around one global point.

The current impactCenter = 0.6 is a shipped heuristic, not a geometric law. The proper fix is a per-gap feasible impact band derived from gap duration, entry speed, arc length, tangent, and preclear/survival probes. Optional LR_IMPACT_ANCHOR_FALLBACK_BISECT=1 can try anchor-Y bisection after a direct failure, but the default impact-anchor path validates directly.
Ranking

Candidate score for one gap

For a contact gap, handoff samples a deterministic candidate prefix, keeps a small pool, adds special candidates, ranks them, and branches on the best three.

score = candidate.cost + future-contact scarcity + state penalty + speed overshoot penalty + air overshoot penalty

Base pool

Sample 14 candidates while searching for the first passing output, or 13 on sparse contact cadences, then widen to 16 for quality search. Rank a pool of 8 and branch on the best 3.

contract K 14/13quality K 16branching 3

Future-contact probe

Preview one future contact with one candidate. A dead end gets a heavy penalty, scarce survivor count gets a smaller penalty, and the preview's local cost is a small ranking signal during contract search.

horizon 1preview K 1cost 0.25

Overshoot control

Speed and air are penalized asymmetrically only when achieved values exceed targets. This is selection-only; it does not alter the candidate generator.

speed 16air 16
Candidate sources

Extra options that lose gracefully

Handoff adds candidates that are still fully physics-validated. They only help when the ranking says they help; otherwise they simply lose to the normal pool.

Catch reuse

On periodic rhythms, a recent sled-relative catch can work again. The compiler translates the latest committed catch from the prefix into the current sled frame and validates the survivor with tryCandidate.

Brake catches

On speed-targeted gaps above the authored minimum, if the current raw speed is already over the authored target's raw px/frame mapping and the target is still inside the mild brake gate, the compiler offers uphill-entry brake catches. Contract search samples 2..3 brake attempts depending on speed ratio; after a passing output exists, quality search may widen the local brake probe to 3..4. Brake catches are excluded from reuse because they are corrective catches, not steady-state rhythm shapes.

Air-support stream

Quality search has one explicitly registered axis-quality stream: low-air gaps can receive one longer, shallow air_support candidate. It is sampled with its own seed, validated through the same impact-anchor and detector gates, and simply loses if it does not improve the ranked options.

Terminal behavior

Partial outputs are first-class

The compiler can return a failing prefix honestly. Nonterminal prefixes are detected through their committed horizon, include a bounded window of future contacts marked missing, and force a failing terminus at the cutoff. Terminal prefixes are scored over the full spec.

Tail completion

For medium-dense skip-free prefixes near the end, handoff tries a short greedy finish when at most six contacts remain.

Polish

Terminal prefixes can be clone-tested by polishLeafVariant. The variant is offered to the same register and only adopted on strict improvement.

Independent per-budget runs

Each requested budget is an independent full run from scratch (no anytime sharing): the budget is an input, and the run returns the strict best-so-far register reached at that budget.

Selection

The best-so-far comparator

Every prefix output, complete or partial, is offered to one strict register. Strict improvement only means equal-quality ties keep the first-seen output, which keeps larger budgets stable.

1
Contract pass
A passing report beats any failing report. Passing means no drifted contacts, no missing contacts, no off-beat landings, and end-of-spec survival.
2
Passing rows
Among passing outputs, higher axis_quality wins. drift_quality is the next tiebreak.
3
Failing rows
Among failing outputs, higher full score wins. Full score includes axis, drift, missing, off-beat, and survival quality.
Budget

Physics work, not wall-clock

The budget unit is simulated rider frames. Cached lr-core reads cost zero; advancing the engine through new frames is charged. Wall-clock is printed for diagnosis only and is not part of scoring.

Charged work

Detector extractions, candidate validation, future previews, polish probes, and metered rider-state reads all contribute when they advance simulation.

Uncharged work

Geometry math, sorting, cache hits, and registry comparisons do not directly simulate physics and are not charged as sim frames.

Policy boundary

Budget is a stop condition. Candidate counts, preview depth, scoring weights, and start search policy are fixed constants.

Kept changes

Commit-by-commit notes

The theme is consistent: selection-based and one-time levers compounded; broad generation changes were volatile.

The search ranks only a small pool and branches three-wide, so generating the old full pool spent budget on candidates that could not affect the frontier. Sampling a deterministic prefix improved node throughput.

The preview is a ranking probe. One future candidate is enough to detect a dead end, so reducing preview work released more budget for actual prefix expansion.
b9f6442Drop preview-cost ranking bias137 -> 140
Preview survivor scarcity was useful; preview local cost biased the current catch toward making the next gap cheap at the expense of current axis quality.

Recent sled-relative catches can be translated and validated cheaply on steady rhythms. This adds candidates without changing the base generator.

Long tracks tended to accumulate speed. Penalizing only over-target speed made the ranking prefer slower existing catches without altering geometry.
28dd652Tune speed overshoot weight192 -> 195
The measured weight of 16 worked better than the lower initial value on the fixed suite.

Air-time showed the same over-target shape as speed. The same asymmetric ranking penalty improved several rows.

Selection cannot pick a slow catch if none exists. Brake candidates create uphill-entry options, then let the normal ranking decide whether they are worth taking.

Lessons

What this history says about future work

The next useful compiler improvements should either reach complete prefixes sooner or improve axis quality without making the budget a policy input.

Levers that held up

  • Selection re-ranking of already-valid candidates.
  • Reuse of known-good catch geometry after validation.
  • One-time start-state exploration.
  • Density-aware allocation of optional work.
  • Cheaper feasibility previews.

Levers to treat carefully

  • Broad per-gap candidate escalation.
  • Geometry changes tied directly to target axes.
  • Late repair passes that steal budget from prefix search.
  • Any mechanism whose behavior changes when the remaining budget changes.
