Line Rider procedural track compiler

handoff compiler

The current v0 compiler is a deterministic prefix search. It turns a musical spec into a rideable Line Rider track by extending one contact gap at a time, scoring every partial output, and returning the best track seen before the simulated-physics budget runs out.

Mental model

Spec -> gaps -> catches -> track

A spec names a duration, contacts, and axis target curves. Contacts are the beats the rider must hit; curves describe what the ride should feel like between those beats.

1
Read the spec
Validate the spec, convert contact times to frames, split the timeline into gaps, and samples each gap's axis targets (from the curves) with the seeded RNG.
2
Choose starts
Resolve the default or manual start. If preroll gives permission and no manual start is set, rank up to ten deterministic initial velocity options with a small opening feasibility probe.
3
Search prefixes
Pop a prefix from the frontier, evaluate it, then extend the next contact gap with the top-ranked candidate catches. Skip-free prefixes are always explored before fallback prefixes.
4
Validate physics
Candidate catches are not guessed into the output. Each survivor is placed into the lr-core engine and measured through detector reports.
5
Return best seen
The strict register prefers contract-passing tracks, then better achieved style. If the budget ends early, the best honest partial output is still available.
speedAuthored pace mapped to raw px/frame.
airHow airborne or grounded the ride should be.
grainHow large and coarse the generated catch geometry feels.

Orientation

The problem, in one picture

A spec is a row of beats the rider must hit on time, plus a target feel for the ride between them. The compiler draws track so the rider lands on every beat and the ride between beats matches the target. The hard part: it is one continuous ride, so every catch you draw changes the state the rider carries into the next beat. Nothing is independent — a locally perfect catch that leaves a bad exit state can make the next beat impossible.

speedmean pace over the gap. Set by where the track sends the rider vertically — downhill gains speed, climbing sheds it.
airfraction of the gap the rider is off the ground. High = lofted hops; low = glued, riding along the track.
graintexture of the catch — the median length of the lines that make it. Short lines feel busy; long lines feel smooth.

Score for a finished, valid track is essentially 1000 · exp(-error / tolerance), where the error is how far the achieved speed/air/grain land from their targets, pooled over every gap. So once a track lands all its beats cleanly, all that is left is precision: how close the feel comes to the target, gap by gap.

Search state

A node is a "track so far"

The search never rebuilds a whole track to try something new. A node is the catches committed up to one beat, the exact rider/engine state at that point, and a little bookkeeping. Extending a node into the next gap is cheap because everything before it is already simulated and frozen.

What the node holds

  • which beat is next — how far the prefix has been built.
  • the committed catches so far (with a marker for any beat that had to be skipped).
  • the engine state — the rider's exact position and velocity at the end of the prefix.
  • the next line id, so new geometry gets stable identifiers.
  • a memoized candidate cache, so re-visiting a node never re-samples.

Plus the choices around it

  • which start (initial condition) this prefix grew from, and its rank.
  • whether the start alternatives have been expanded yet.
  • how many beats this branch has skipped — used to deprioritize it.
  • a flag to defer expansion after a skip, so honest partial outputs are scored before the search digs deeper.
One catch

How a single landing is built

A candidate is not a line picked from the canvas. The compiler predicts where the rider will be at the beat, samples an arc shape, slides the whole arc so one chosen point on it sits exactly under the rider at the beat frame, then asks the real physics engine whether it truly lands on time and survives. Only survivors get measured.

1
Predict the rider
Run the prefix forward to the beat frame without any new track. Record the rider's velocity and pick the lowest point of the sled as the spot the catch must meet.
2
Sample an arc shape
Pick length, segment count, entry and exit angles, and curvature. Grain steers segment count; air steers how grounded the ride-in and ride-out are; speed steers whether the exit climbs (sheds speed) or dives (gains it). At this point the arc is still abstract geometry anchored at the origin.
3
Anchor it at the impact point
Choose a point along the arc to be the contact, then translate the whole arc so that point lands under the predicted sled at the beat frame. Moving the impact point changes the catch's shape, clearance, and which parts could collide with the rider before the beat.
4
Pre-clear, then validate with physics
Reject candidates whose lines would hit the rider before the beat. Then add the lines to lr-core and read the detector: the fit is kept only if the rider survives, an owned landing fires within ±1 frame of the beat, and no stray landing happens first. Survivors are then measured for speed, air, and grain.
The impact point is a single shipped heuristic, not a geometric law. It is one of the reasons the generator can only make a limited family of catch shapes — a real lever (see the frontier today) is a smarter, per-gap choice of shape and impact rather than translating one family.
The search tree

Every beat forks the track

At each beat the ranker keeps the best three catches, so a node spawns (at most) three children. Partial tracks therefore form a tree: depth is the beat index, branches are alternative catches. The tree is astronomically large; the budget decides how much of it gets walked.

Walking the tree

Dive on the best, keep the best, back up when stuck

The walk is depth-first: children are pushed best-first and the most recent is always popped, so it dives down the most promising catch to reach a complete track quickly. A separate best-so-far register watches every prefix that goes by and remembers the single best complete track seen anywhere — so the answer is not the greedy path, it is the global best the walk happened to touch.

Two stacks, clean first

The frontier is split: prefixes that have landed every beat so far (the pass stack) are drained before prefixes that had to skip a beat (the fallback stack). So a clean branch always gets priority, and a skipped branch is only explored when nothing clean remains.

Backing up & far-back pulses

When a dive dead-ends or finishes, the stack naturally backs up to the next sibling. Periodically the walk also reaches far back to an old, shallow node it skipped past — so one strong-looking early catch can never monopolize the whole budget and starve better early choices.

depth-first dive register = global best pass before fallback far-back pulse partial outputs scored too
Ranking

Which three catches survive

For each gap the compiler samples a pool of candidates, scores them, and branches on the best three. Lower score is better. Four of the five terms are about this beat or the immediate exit state; only one looks forward, and only by a single beat.

score = candidate.cost # local fit: how close speed / air / grain land this gap + future scarcity # peek ONE beat ahead: does it still have catches? (dead end = heavy penalty) + preview cost # how cheap the best next catch looked, one beat ahead + exit-state penalty # punish leaving the rider too steep / too vertical + overshoot penalty # punish speed/air that lands OVER target (anti-creep)

Local fit

The squared distance from this gap's speed, air, and grain targets, weighted equally. This is the bulk of the signal.

pool 8branch 3

One-beat preview

Tentatively commit the catch, look one beat ahead, and check how many viable catches survive there and how cheap the best one is. A dead end is heavily penalized; few survivors a little. This is the only forward-looking term.

horizon 1

Exit state & overshoot

Penalize an exit that is too vertical or too steep, and penalize speed/air that overshoots target (catches are net-downhill, so the rider tends to creep faster over time). Selection-only — it never changes the geometry, only which candidate wins.

The single-beat horizon is exactly the spot where ranking is blind to the long run: a catch that looks great now and one beat ahead can still steer the rider into a state that quietly degrades quality three beats later. Widening this horizon into a real multi-gap objective is the most promising open direction.
Extra candidates

Options that lose gracefully

Besides the normal pool, the compiler offers a few special catches. They are all fully physics-validated and simply lose the ranking when they do not help — so they can only ever add a better option, never remove a good one.

Catch reuse

On a steady rhythm, a recent catch translated to the current sled frame can land again — a cheap way to keep a periodic ride consistent.

Brake catches

When the rider is running over target speed, uphill-entry catches that bleed speed are offered. On specs that are not creeping they simply lose.

Air-support stream

For low-air (glued) gaps, a longer, shallower catch is offered to keep the rider riding rather than hopping. Validated through the same gates.

When nothing lands

Rescue, skip, stay honest

Sometimes no sampled catch lands a required beat. The compiler does not give up or lie about it.

1
Rescue
At a true dead end, sample many more candidates than usual — and for very tight (sub-0.3s) beats, sample more still — before giving up on the beat.
2
Skip
If rescue still finds nothing, mark the beat skipped, drop the branch to the fallback stack, and keep going. A skipped beat fails the contract (scores near zero) but lets the walk reach the end.
3
Partials are first-class
A prefix that never finished is scored honestly for what it achieved, with the unreached beats marked missing. So the register always has something to return, and a half-built track never masquerades as complete.

Two speculative finishers also run: tail completion greedily finishes a near-complete clean prefix early, and polish clone-tests small tweaks of a finished track — both only ever adopted on a strict register improvement.

The budget

The clock is rider-frames, not wall-time

Work is metered in simulated rider frames: every candidate trial costs the frames lr-core actually steps. The walk runs until the budget is spent, then returns the register's best. Wall-clock is never scored, so a faster machine cannot buy a better track.

More budget = more tree

A bigger budget simply walks more of the same deterministic tree: more candidates per gap early on, more branches explored, more of the frontier revisited. The policy is fixed; the budget is just how far it gets to look.

Independent per budget

Each budget on the curve is a full run from scratch — there is no shared "anytime" checkpoint curve. The same (spec, seed, budget) always produces a byte-identical track.

The frontier today

Where extra budget stops converting

Past a moderate budget the score plateaus, and the reason is specific and measured: the wall is candidate generation, not the search. More candidates, more start options, wider branching, and more search diversity were each tried at high budget and were all neutral — the search is already finding the best catches the current generator can make, and those are not good enough.

Air is the limiting axis

Across specs, the dominant error is the air axis — the rider carries too much air on glued targets, and the generator cannot produce lower-air catches that still land on-beat. Halving the air error alone would move the headline most of the way to its target.

Ranking sees one beat

The only forward-looking term is the one-beat preview, so ranking is mostly local. A deeper, multi-gap objective — "does this catch lead toward a state compatible with the rest of the track?" — is an open lever, and a naturally budget-aware one.

So: generation, then ranking

A deeper lookahead only helps if the candidate pool contains better catches to choose among. The two levers compound: richer catch generation (especially for air), and a forward-looking objective to choose among the richer pool.

Selection

The best-so-far comparator

Every prefix output, complete or partial, is offered to one strict register. Strict improvement only means equal-quality ties keep the first-seen output, which keeps larger budgets stable.

1
Contract pass
A passing report beats any failing report. Passing means no drifted contacts, no missing contacts, no off-beat landings, and end-of-spec survival.
2
Passing rows
Among passing outputs, higher axis_quality wins. drift_quality is the next tiebreak.
3
Failing rows
Among failing outputs, higher full score wins. Full score includes axis, drift, missing, off-beat, and survival quality.
Budget

Physics work, not wall-clock

The budget unit is simulated rider frames. Cached lr-core reads cost zero; advancing the engine through new frames is charged. Wall-clock is printed for diagnosis only and is not part of scoring.

Charged work

Detector extractions, candidate validation, future previews, polish probes, and metered rider-state reads all contribute when they advance simulation.

Uncharged work

Geometry math, sorting, cache hits, and registry comparisons do not directly simulate physics and are not charged as sim frames.

Policy boundary

Budget is a stop condition. Candidate counts, preview depth, scoring weights, and start search policy are fixed constants.

Lessons

What this history says about future work

The next useful compiler improvements should either reach complete prefixes sooner or improve axis quality without making the budget a policy input.

Levers that held up

  • Selection re-ranking of already-valid candidates.
  • Reuse of known-good catch geometry after validation.
  • One-time start-state exploration.
  • Density-aware allocation of optional work.
  • Cheaper feasibility previews.

Levers to treat carefully

  • Broad per-gap candidate escalation.
  • Geometry changes tied directly to target axes.
  • Late repair passes that steal budget from prefix search.
  • Any mechanism whose behavior changes when the remaining budget changes.
