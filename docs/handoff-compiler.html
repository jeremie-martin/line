Line Rider procedural track compiler

handoff compiler

The current v0 compiler is a deterministic prefix search. It turns a musical spec into a rideable Line Rider track by extending one contact gap at a time, building a physics-validated candidate pool for each beat, and returning the best output seen before the simulated-physics budget is spent. The requested budget is now a real policy input: contract breadth, quality breadth, forward evaluation, multi-base aiming, tail completion, and repair all use deterministic budget gates while every committed candidate still comes from exact lr-core validation.

Default view

The compiler in one page

Handoff compiles from authored intent to physics-validated geometry. The policy is deterministic for a given spec, seed, and budget. Each budget is an independent full run, and the target budget controls how much work the search can spend on breadth, ranking, aiming, tail completion, and repair. Candidate pools contain ordinary samples plus model-proposed arc variants; every candidate that can be committed has still been simulated and measured by lr-core.

Mental model

Spec -> gaps -> catches -> track

A spec names a duration, contacts, and axis target curves. Contacts are the beats the rider must hit; curves describe what the ride should feel like between those beats.

1
Read the spec
Validate the spec, convert contact times to frames, split the timeline into gaps, drop physically uncatchable pre-floor contacts, sample each gap's axis targets with the seeded RNG, and resolve per-beat impact into the terminating gap target.
2
Choose starts
Resolve the default or manual start. If preroll gives permission and no manual start is set, rank up to ten deterministic initial velocity options with charged forward start evaluation. Higher target budgets can also admit ballistic and support-line starts for difficult openings.
3
Search prefixes
Pop a prefix from the frontier, evaluate it, then extend the next contact gap with the top-ranked candidate catches. Skip-free prefixes are explored before fallback prefixes, and scarce budgets can narrow contract breadth so the run reaches a complete track sooner.
4
Propose and validate physics
Sampled catches and aimed variants enter the same pool. Aimed variants are chosen by a model-only current-quality times readiness objective. The pool itself is quality-objective sorted by default, but every aimed or sampled candidate is placed into lr-core and measured before the search can select it.
5
Return best seen
The strict register prefers contract-passing tracks, then better achieved style. If the budget ends early, the best honest partial output is still available.

Orientation

The problem, in one picture

A spec is a row of beats the rider must hit on time, plus a target feel for the ride between them. The compiler draws track so the rider lands on every beat and the ride between beats matches the target. The hard part: it is one continuous ride, so every catch you draw changes the speed and direction the rider carries into the next beat. Nothing is independent — a locally perfect catch that leaves a bad arrival state can make the next beat weak or impossible.

speedmean pace over the gap. Set by where the track sends the rider vertically — downhill gains speed, climbing sheds it.
airfraction of the gap the rider is off the ground. High = lofted hops; low = glued, riding along the track.
elevationnet climb or plunge, normalized to what the current speed can realistically support.
amplitudeheight of the trajectory bow between takeoff and landing; separate from how long the rider is airborne.
impactper-beat landing intensity: how much the catch redirects the center-of-mass velocity.
grainlegacy measured texture, retained for reports but not authored as an active target.

Score for a finished, valid track is essentially 1000 · exp(-error / tolerance), where the error is how far the achieved authored axes and contact impacts land from their targets, pooled over the track. So once a track lands all its beats cleanly, all that is left is precision: how close the feel comes to the target, gap by gap.

Search state

A node is a "track so far"

The search never rebuilds a whole track to try something new. A node is the catches committed up to one beat, the exact rider/engine state at that point, and a little bookkeeping. Extending a node into the next gap is cheap because everything before it is already simulated and frozen.

What the node holds

  • which beat is next — how far the prefix has been built.
  • the committed catches so far (with a marker for any beat that had to be skipped).
  • the engine state — the rider's exact position and velocity at the end of the prefix.
  • the next line id, so new geometry gets stable identifiers.
  • a memoized candidate cache, so re-visiting a node never re-samples.

Plus the choices around it

  • which start (initial condition) this prefix grew from, and its rank.
  • whether the start alternatives have been expanded yet.
  • how many beats this branch has skipped — used to deprioritize it.
  • a flag to defer expansion after a skip, so honest partial outputs are scored before the search digs deeper.
One catch

How arc-state aiming works

The compiler still begins with ordinary sampled catches. The aiming layer refines the leading quality-sorted pool candidates, treats small arc edits as knobs, learns a local response model from a few metered probe rides, scores many virtual edits cheaply, and sends only the best proposals back through exact physics validation.

1
Build a real pool first
Normal sampling proposes catch geometry from the current prefix state: length, segment count, contact point, angles, curvature, and any sampler templates. Each sampled catch is pre-cleared, simulated, gate-checked, and measured before it can enter the sorted pool.
2
Pick one base catch
The proposer refines the first quality-ranked base at low budgets. At mature target budgets it can refine up to three leading bases, keeping probe work bounded while ordinary samples, reuse, brake/startup streams, and templates still compete against aimed proposals.
3
Probe knob responses
Exit pitch and whole-arc rotation are probed together with the shared joint design. Production defaults to a five-row cross and can opt into a nine-row grid; both feed the same local response model.
4
Fit small local models
Each probe ride yields the whole rider-state vector at the next beat: position, velocity, speed, CoM velocity angle, sled pose, and pose rate. A richer probe can also measure current-gap axes, current impact when defined, and local cost. The generic shape is a joint output-vector model over arc knobs; today's shipped instance fits a shared response model for current axes plus the next-arrival state, then scores edits with the shared current-quality times readiness objective.
5
Sweep virtual edits
The code scans pitch x rotation knob pairs inside the probed span. Those virtual edits are cheap model evaluations, not simulations. The current objective is current-gap quality times composite next-gap readiness.
6
Emit, then measure
In the current implementation, the lane emits at most two proposals per refined base. Every emitted proposal is then tried through tryCandidateLines; ranking and commits consume only those exact measured results.
predicted_outputs(pitchDeg, rotateDeg) = joint_response_model(pitchDeg, rotateDeg) proposal_score(pitchDeg, rotateDeg) = current_axis_quality(predicted_current_axes) × next_gap_readiness(predicted_next_state) committed_score = exact gates + exact measured axes + handoff score / forward eval
The generic idea is broader than the current code: learn a cheap predictor that can score many edits before paying for simulation, then emit the top-k proposals into exact validation. The current instance emits the top two variants per refined base, may refine up to three bases above the maturity gate, predicts current-gap axes plus the next-arrival state with a shared joint response model, and production still measures emitted proposals exactly.
The search tree

Every beat forks the track

At each beat the ranker keeps at most three catches; scarce contract budgets can temporarily narrow that branching. Partial tracks therefore form a tree: depth is the beat index, branches are alternative catches. The tree is astronomically large, and each target budget chooses a deterministic route through it.

Walking the tree

Dive on the best, keep the best, back up when stuck

The walk is depth-first: children are pushed best-first and the most recent is always popped, so it dives down the most promising catch to reach a complete track quickly. A separate best-so-far register watches every offered output and remembers the best comparator key seen so far. The answer is not the greedy path; it is the best complete or honest partial output the walk touched under that budget.

Two stacks, clean first

The frontier is split: prefixes that have landed every beat so far (the pass stack) are drained before prefixes that had to skip a beat (the fallback stack). So a clean branch always gets priority, and a skipped branch is only explored when nothing clean remains.

Backing up & far-back pulses

When a dive dead-ends or finishes, the stack naturally backs up to the next sibling. Periodically the walk also reaches far back to an old, shallow node it skipped past — so one strong-looking early catch is less likely to monopolize the quality phase and starve better early choices.

depth-first dive register = global best pass before fallback far-back pulse partial outputs scored too
Ranking

Which three catches survive

For each gap the compiler builds a candidate pool, then branches on the best measured candidates. There are three separate scoring moments: a model-only objective that decides which aimed variants are worth simulating, a zero-extra-sim quality objective that sorts the measured pool, and the search ranker that decides among already validated candidates.

candidate pool = sampled catches + aimed proposals # top 2 per refined base, exact-validated + sampler templates # impact-shaped geometry inside the normal sample stream + reuse / brake / startup streams # deterministic extras, all exact-validated pool ordering = current quality x next readiness # measured axes + free/predicted arrival state branch ranking = true-score forward eval # mature budgets: charged rollout, rank by metric value reached or measured handoff score # local cost + preview scarcity + state/overshoot penalties

Proposer score

The enum lane scores a dense grid of virtual deltas without simulating them. That score only decides which variants enter the pool; it never commits a track.

model-onlytop-2 per base

Pool sort

The default pool order uses achieved current-gap axes and the next-arrival state. If the next state was captured by the candidate ride it is free; otherwise the ranker uses ballistic prediction without charging another ride.

measured axespredict-only

Branch rank

Once a candidate is in the pool, branch ranking uses measured handoff score below the forward-eval gate and charged true-score rollout at mature budgets. Prediction error is telemetry, not authority.

This separation is deliberate. The model objective may be aggressive because predictions only choose proposals; search still chooses from exact measurements. Pool sorting may use predicted arrival state, but candidate truth still comes from gate checks and measured axes. Mature forward-eval ranks by charged rollout value.
Extra candidates

Options that lose gracefully

Besides normal random samples, the compiler offers a few deterministic ways to enrich the pool. They all go through the same gates and measured ranking. Sampler templates are geometry families; the enumerative proposer is the only aiming mechanism.

Enumerative proposer

The production aimer scores virtual pitch and rotation edits, emits at most two proposals per refined base, and never bypasses exact validation. The old speed, angle, rotate-fallback, scoop, and climb-defer triggers are deleted.

Impact templates

Impact-pressure gaps can add shaped catch geometry inside the sampler: impact curvature, post-turn shaping, arrival pressure, and the SLAM-HOP template. These are geometry families, not second aim lanes.

Pool extras

Recent-catch reuse, uphill brake catches, and startup catches can add candidates. Each is deterministic, memoized where useful, and discarded unless the measured ranker wants it.

Repair and tails

Tail completion can greedily finish promising near-complete prefixes. Mature-budget repair restarts from weak gaps with fresh deterministic seeds. Polish is an optional clone-test mode, not part of the default path.

When nothing lands

Rescue, skip, stay honest

Sometimes no sampled catch lands a required beat. The compiler does not give up or lie about it.

1
Rescue
At a true dead end, sample many more candidates than usual. Moderate-speed overshoot states get a brake-oriented rescue, very tight (sub-0.3s) beats can trigger a larger short-deadline batch, and early dead ends can try startup catches.
2
Skip
If rescue still finds nothing, mark the beat skipped, drop the branch to the fallback stack, and keep going. A skipped beat fails the contract (scores near zero) but lets the walk reach the end.
3
Partials are first-class
A prefix that never finished is scored honestly for what it achieved, with the unreached beats marked missing. So the register always has something to return, and a half-built track never masquerades as complete.

Tail completion can greedily finish a near-complete clean prefix early. At mature budgets, default repair may restart the real search from a weak committed gap with a fresh deterministic seed; the register adopts only strict improvements. Polish is available as an optional clone-test mode.

The budget

The clock is rider-frames, not wall-time

Work is metered in simulated rider frames: every candidate trial costs the frames lr-core actually steps. The target budget is fixed for one compile and gates optional work; the run returns the register's best when the budget is spent or the frontier is exhausted. Wall-clock is never scored, so a faster machine cannot buy a better track.

Budget gates effort

A bigger budget enables more expensive deterministic policy, including wider quality sampling, multi-base aiming, forward evaluation, larger tail windows, and repair. Physics validation still decides what can be committed.

Independent per budget

Each budget on the curve is a full run from scratch — there is no shared "anytime" checkpoint curve. The same (spec, seed, budget) produces a byte-identical track for a given compiler build; cross-budget monotonicity is diagnostic, not a contract.

The frontier today

Where extra budget stops converting

The current frontier is budget allocation and ranking, not a return to hand-tuned aim lanes. The compiler has one aiming mechanism: the enumerative proposer. New capability belongs in the inner model, readiness/objective terms, sampler templates, or deterministic budget gates, then exact validation and measured ranking decide whether it survives.

One proposer remains

The promoted proposer fits a joint local response from shared short probe rides, enumerates knob pairs in the model, and optimizes current quality times composite readiness.

Budget growth path

Mature compiles can spend on multi-base aiming, charged forward-eval rollouts, tail completion, and weak-gap repair. Low budgets keep leaner contract search so they can finish.

Selection is a later gate

Readiness is now part of shared pool ordering. The branch judge is still measured handoff score or charged rollout value; prior attempts to widen rollout visibility at impact gaps were negative.

Selection

The best-so-far comparator

Every prefix output, complete or partial, is offered to one strict register. Strict improvement only means equal-quality ties keep the first-seen output inside that run. Because each budget is a separate compile and may take different budget-gated policy, cross-budget monotonicity is reported as a diagnostic rather than guaranteed.

1
Contract pass
A passing report beats any failing report. Passing means no drifted contacts, no missing contacts, no off-beat landings, and end-of-spec survival.
2
Passing rows
Among passing outputs, higher axis_quality wins. drift_quality is the next tiebreak.
3
Failing rows
Among failing outputs, higher full score wins. Full score includes axis, drift, missing, off-beat, and survival quality.
Budget

Physics work, not wall-clock

The budget unit is simulated rider frames. Cached lr-core reads cost zero; advancing the engine through new frames is charged. Wall-clock is printed for diagnosis only and is not part of scoring.

Charged work

Detector extractions, candidate validation, future previews, repair/polish probes, and metered rider-state reads all contribute when they advance simulation.

Uncharged work

Geometry math, sorting, cache hits, and registry comparisons do not directly simulate physics and are not charged as sim frames.

Policy boundary

Budget is both the work unit and an effort-allocation input. Candidate truth remains exact simulation and measured reports.

Kept changes

Commit-by-commit notes

The theme is consistent: selection-based and one-time levers compounded; broad generation changes were volatile.

The search ranks only a small pool and branches three-wide, so generating the old full pool spent budget on candidates that could not affect the frontier. Sampling a deterministic prefix improved node throughput.
1c80246Halve feasibility-preview cost89 -> 137
The preview is a ranking probe. One future candidate is enough to detect a dead end, so reducing preview work released more budget for actual prefix expansion.
b9f6442Drop preview-cost ranking bias137 -> 140
Preview survivor scarcity was useful; preview local cost biased the current catch toward making the next gap cheap at the expense of current axis quality.
c9801a0Add catch reuse for periodic rhythms140 -> 188
Recent sled-relative catches can be translated and validated cheaply on steady rhythms. This adds candidates without changing the base generator.
c49b19fPenalize speed overshoot in ranking188 -> 192
Long tracks tended to accumulate speed. Penalizing only over-target speed made the ranking prefer slower existing catches without altering geometry.
28dd652Tune speed overshoot weight192 -> 195
The measured weight of 16 worked better than the lower initial value on the fixed suite.
8ab8594Add air overshoot penalty195 -> 200
Air-time showed the same over-target shape as speed. The same asymmetric ranking penalty improved several rows.

Selection cannot pick a slow catch if none exists. Brake candidates create uphill-entry options, then let the normal ranking decide whether they are worth taking.

Speed creep is hard to recover late. Triggering brakes as soon as speed exceeds target prevented accumulated damage.

Lessons

What this history says about future work

The next useful compiler improvements should either reach complete prefixes sooner, spend budget more deliberately, or improve axis quality without bypassing exact physics validation.

Levers that held up

  • Selection re-ranking of already-valid candidates.
  • Reuse of known-good catch geometry after validation.
  • One-time start-state exploration.
  • Density-aware allocation of optional work.
  • Target-budget gates for expensive quality work.
  • Cheaper feasibility previews.

Levers to treat carefully

  • Broad per-gap candidate escalation.
  • Geometry changes tied directly to target axes.
  • Late repair passes that starve first completion.
  • Policies that react to consumed frames instead of the compile's fixed target budget.
